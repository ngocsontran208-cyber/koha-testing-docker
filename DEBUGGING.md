# KTD Debugging with DAP

## Overview

Perl debugging inside KTD using VSCode (or any DAP-compatible editor) with
Gerald Richter's Perl::LanguageServer extension.

**Key features:**
- Set breakpoints and step through Koha code
- Debug tests (`prove`) with full variable inspection
- Debug Plack (web requests) — hit the app from your browser, breakpoints fire
- Works through the normal Apache proxy — no extra ports needed

## How it works

- Perl::LanguageServer implements both LSP (syntax, symbols) and DAP (debugging)
- VSCode runs the language server inside the KTD container via `docker exec`
- For debugging, VSCode launches processes inside the container under the debugger
- Plack debugging uses Twiggy (single-process, no forking) on the same unix socket
  that Apache proxies to — so the app behaves normally

## Quick start

```bash
ktd --debug up -d
```

This generates `.vscode/{launch.json,tasks.json,settings.json}` in your `$SYNC_REPO`
with the correct container name and path mappings.

### VSCode extension

Install **"Perl"** by Gerald Richter (extension ID: `richterger.perl`).

### Debug a test

1. Open a `.t` file
2. Set breakpoints
3. Press F5 → select "KTD: Debug current test"
4. Step through, inspect variables

### Debug Plack (web requests)

1. Select "KTD: Plack (debug)" and press F5
2. The preLaunchTask stops the normal koha-plack
3. Twiggy starts on the plack socket under the debugger
4. Open `http://localhost:8080` or `http://localhost:8081` (or your traefik URLs)
5. Breakpoints fire on every request

### Restart normal Plack

When done debugging, restart the normal Plack:

```bash
ktd --shell --run "sudo service koha-common start"
```

## Architecture

```

│  Host (macOS)                                           │
│                                                         │
│  VSCode + richterger.perl extension                     │
│    │                                                    │
│    │ docker exec (stdio) ──── DAP protocol              │
│    ▼                                                    │
├─────────────────────────────────────────────────────────┤
│  KTD Container                                          │
│                                                         │
│  Perl::LanguageServer (LSP + DAP)                       │
│    │                                                    │
│    ├─► perl -d test.t          (test debugging)         │
│    │                                                    │
│    └─► plackup --server Twiggy (plack debugging)        │
│            │                                            │
│            ▼                                            │
│        /var/run/koha/kohadev/plack.sock                 │
│            ▲                                            │
│            │                                            │
│        Apache (ProxyPass)                               │
│            │                                            │
├────────────┼────────────────────────────────────────────┤
│            ▼                                            │
│  Browser → localhost:8080/8081 (or traefik URLs)        │
└─────────────────────────────────────────────────────────┘
```

## Packages added to KTD image

- `libperl-languageserver-perl` — LSP + DAP adapter
- `Twiggy` (CPAN) — single-process async PSGI server for debug mode

## Files generated by `ktd --debug`

| File | Purpose |
|------|---------|
| `.vscode/settings.json` | Tells the Perl extension to run inside the container |
| `.vscode/launch.json` | Debug configurations (test + plack) |
| `.vscode/tasks.json` | preLaunchTask to stop normal plack before debug |

## Worktree support

Each worktree gets its own `.vscode/` directory with the correct container name
(from `--name`). If the launch.json already exists but targets a different container,
`ktd --debug` will error and ask you to fix it.

## Limitations

- Perl DAP only supports **launch** mode (no attach to running process)
- The IDE must start the process — you cannot debug an already-running Plack
- Twiggy is single-process: one request at a time during debug sessions
- `reloadModules: true` in launch.json auto-reloads changed modules between requests
